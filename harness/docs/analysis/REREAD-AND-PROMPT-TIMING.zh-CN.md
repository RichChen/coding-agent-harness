# 重复阅读与提示时机：离线分析

日期：2026-11-06。只读已有运行产物，不调用模型，不启动 Docker。脚本和输出在 `scripts/analysis/reread/`，复现方法见第 8 节。

## 结论

1. **重复读占工具调用的 15.5%（A5）到 40.3%（CR-2）。** A6-R 30.6%，P4 提示时机 53 次 31.3%，P4 首轮真实任务 25 次调用里有 10 次。
2. **85–94% 的重复读发生时，之前那次结果已经被遮蔽成占位符。** 原文仍完整在视图里的只占 4–10%。分析开始前写下的标准是"大部分重复读发生在原文被遮蔽之后"，四个实验都远超过一半。
3. **重复读集中在原文刚被遮蔽之后。** 所有运行的 micro-compact 都只保留最近 4 条工具结果原文。重复读距离上一次相同读取，相隔 1–4 次调用（原文还在）的每档只有 0.3–8%；相隔 5–6 次（原文刚被换成占位符）的占 42–56%。
4. **和是否解出的关系，主要是运行长度造成的。** 在 CR-2 里，同一道题解出的运行全程重复读占比平均低 17.9 个百分点（32 道题里 29 道更低）。但未解出的运行中位要 43 次工具调用，解出的只要 17 次；只看前 15 次调用，差值缩到 −2.4 个百分点（18 低 / 12 高）。A5、A6-R 两种算法都接近 0。没有证据说明减少重复读能提高解出率。
5. **提示时机：M 组的 5 次通过，有 3 次和中途提示无关。** 9030 的 3 次 M 都在提示到达前就已经编辑。和提示可能有关的只有 8945 的 2 次：提示后 1–2 次请求开始编辑，同题 N、I 0/6。44 次失败的运行全都没有编辑过。这些和 v4 已有的 `process-analysis-v1.md` 一致。
6. **判断：下一轮付费实验应该做上下文策略，不做提示时机。** 设计和预先写下的阈值见第 6 节。

## 1. 数据和"重复读"的定义

| 实验 | 路径 | 纳入运行 | 剔除 |
|---|---|---:|---|
| A5 | `runs/a5-main/*/*/r*` | 392 | 7 次 infra 退役重跑 |
| A6-R | `runs/a6-retry/*/*/*/r*` | 318 | 31 次 infra 退役重跑 |
| CR-2 | `runs/cr2-main/*/*/r*` | 1108 | 159 次 infra 退役重跑、12 次 `infra_error` |
| P4 提示时机 | v2/v3/v4 三个批次根目录 | 53 | 1 次无效候选、1 次未知结果（按 `scripts/audit/errata_2026_11/e3_p4_scale54_final.json` 的分配表） |
| P4 首轮 | `<artifacts>/p4-sphinx8721-20261030-01/solve` | 1 | — |

配置标签：A5 的 b0 是基线，b2 加记忆卡片；A6-R 是 A5 b0 失败题的第二次尝试，r0 用同样的 prompt，r1 附上上次尝试的记录；CR-2 的 n 是基线，p 是预取检索，t 是检索工具，o 是直接给出正确文件的上限参照。所有运行的遮蔽设置相同：micro-compact，`keep_recent=4`。

**读取单元**（`reads.py`）：
- `read_file`：按输出里的行号取实际返回的行范围（P4 每次最多返回 100 行，参数里的 limit 不可靠）。
- `run_command` 里的 `cat`/`nl`（整文件）、`sed -n 'A,Bp'`、`head`、`tail`、`awk 'NR>=A && NR<=B'`。管道后段的 `sed`/`head`/`grep` 会收窄前面的单文件 `cat`。
- 搜索：`search_code`，以及 `grep`/`rg`/`git grep`。同一模式加同一组路径才算同一次搜索，`-n`、`-A` 等选项忽略；基本正则的 `\|` 写法当作 `|`。

**写入**：编辑工具，重定向，`sed -i`，`tee`，`cp`/`mv`/`rm`，`git checkout` 等。写到某个目录，也算写到它下面的文件。运行代码的命令（python、pytest、sphinx-build、make 等）可能改动工作区外的临时目录和构建输出目录，视为写入这些位置。`git stash`、`patch` 这类写到不明位置的命令视为写入所有文件。

**重复读**：某个读取单元已有至少 20% 被之前的读取覆盖，就算这个单元重复。这里只算更早的模型步发出、中间没有写入碰过的读取；同一步并行发出的调用互相看不到结果，不算。一次调用只要有一个单元重复，就算重复读调用。20% 的下限是为了排除顺序翻页，即下一页从上一页最后一行开始的情况。如果只有中间被写入改过的旧读取能达到 20%，记作"写后重读"，不算重复读。"全覆盖重复读"指所有单元都重复，并且每个单元至少 80% 已读过。

**视图状态**：取该步 `context.prepared` 里实际发给模型的视图，找出这些更早调用对应的工具消息。按每个重复单元判断：
- 原文：仍原样在视图里的部分覆盖至少 80%。
- 部分：原样部分覆盖 20–80%。
- 已遮蔽：原样部分不到 20%，并且有 `[Elided result of ...]` 占位符。
- 不在视图：其余情况。

所有重复单元都是原文时，整次调用算原文；有任一单元是原文或部分时，算部分；否则看是已遮蔽还是不在视图。本次数据里没有出现"不在视图"。

## 2. 人工抽样核对

核对做了两轮。

**第一轮（调参样本）**：按实验分层抽了 84 条：每个实验 12 条重复读、6 条未判为重复读的读取、3 条写后重读。逐条对照原始调用列表核对后，发现第一版规则有这些问题：
- 误报 3 条。其中 2 条是只重叠 1 行的顺序翻页；1 条是 grep 的通配路径没按当前目录展开，把两个不同临时目录当成了同一路径。
- 漏报 1 条。
- 视图状态错 7 条。都是只有 1 行重叠的原文被算成"部分可见"，P4 里尤其多。

据此加了：20% 的覆盖下限、目录写入、运行命令改动输出目录、通配路径展开。修正后的规则在这份样本上只剩 1 条漏报。但规则是照着这份样本改的，这个结果偏乐观，不作为误判率。

**第二轮（留出样本）**：规则定下后，换一个随机种子新抽 56 条（每个实验 8 + 4 + 2），只核对一次，不再改规则。结果：

| 项 | 结果 | 95% 区间（精确二项） |
|---|---|---|
| 判为重复读里的误报 | 0 / 32 | 0–10.9% |
| 未判为重复读里的漏报（含写后重读） | 1 / 24 | 0.1–21.1% |
| 视图状态（真重复读中） | 32 / 32 正确 | 89.1–100% |
| 写后重读的排除 | 8 / 8 正确 | — |

那条漏报是两次 `search_code` 用了同样三个备选项，只是顺序不同。另有 2 条近似重复按定义不算：后一次的模式是前一次的子项或多了一项。这说明定义偏保守，重复读的比例更可能被低估，而不是高估。抽样是按分类器自己的标签分层、每层固定数量，所以这些是分层内的比率，不是总体比率。只有一名核对者，没有盲法。

明细：`out/manual_sample_holdout.json`、`out/manual_review_holdout.json`、`out/manual_review_holdout_score.json`。调参样本对应 `*_tuning*` 三个文件，分数文件里同时列出第一版和修正后规则在这份样本上的结果。

## 5. 判断：下一轮付费实验做上下文策略

**依据：**
1. **覆盖面。** 四个实验、全部配置都有重复读，占工具调用的 15–40%。其中 85–94% 读的是已被遮蔽的内容。按分析开始前写下的"大部分"标准（超过一半），结论明确，而且对误判不敏感：留出样本里视图状态 32 / 32 正确，误报 0 / 32。
2. **机制清楚。** 重复读集中在原文刚滑出最近 4 条窗口的位置（间隔 5–6 占 42–56%，间隔 2–4 每档不到 3%），可以直接改的参数也很明确。
3. **在有预算上限的场景里直接占用调用。** P4 分界之后 60–79% 的调用是重复读，而多数运行最后是预算耗尽结束的。
4. **提示时机的证据太窄。** M 比 N、I 多出的通过，全部来自 8945 一道题的 2 次运行；9030 的通过和提示无关。为了一道题上 2 对 0（M 2 / 3，N、I 合计 0 / 6）做付费实验，样本量撑不起来。

**需要说清楚的限制：** 第 3.3 节显示，控制运行长度后，重复读和解出几乎无关。所以上下文策略的预期收益是"省调用、省费用、可能更早进入编辑"，不是"提高解出率"。下一轮的主指标应该是过程指标，解出率只作描述。另外，保留更多原文会让每次请求的输入变长，在按费用计预算的场景里可能抵消省下的调用次数，必须把成本作为护栏指标。

**关于阈值：** 本分析的指标和阈值不是在看数据之前冻结的。唯一在分析开始前写下的标准是"大部分重复读发生在原文被遮蔽之后"。重复读的定义在第一轮人工核对后调整过一次，所以误判率用的是之后新抽的留出样本。下一节的阈值在任何新数据产生之前写下。

## 6. 下一轮实验的设计（阈值在此预先写定）

- **对比**：A = 现行 micro-compact（`keep_recent=4`）；B = `keep_recent=8`。选 8 是因为现有数据里 74–83% 的重复读间隔不超过 8。不加第三组：第 3.2 节的 `sed` 对比显示，没有"re-read if needed"那句话也照样重读，改措辞的优先级低于保留原文。
- **任务和次数**：从 CR-2 的 56 道题里用固定种子随机抽 30 道，用 n 组 prompt。每题每组 3 次，共 180 次，按题配对。用 CR-2 n 组的重复次数估算，按题配对差值的标准差约 13 个百分点，30 题 × 3 次时 95% 区间半宽约 4 个百分点。
- **主指标**：重复读占工具调用的比例，按本文定义和脚本计算（规则冻结在本次提交的版本）。每题先对 3 次取平均，再算 B − A，按题 bootstrap 95% 区间（10000 次，种子事先固定）。
- **判定规则：**
  - B − A ≤ −10 个百分点，并且区间上界 < −5 → 判定"遮蔽策略导致了可避免的重复读"，进入 P4 预算场景复测。
  - 点估计 > −5 个百分点 → 判定重复读主要是模型自身行为，上下文方向不再追加投入。
  - 介于两者之间 → 不下结论，只报告。
- **成本护栏**：B 每次运行的输入 token 总量，按题中位数相对 A 的增幅不超过 30%。超过时，即使主指标达标也不直接采用 `keep_recent=8`，改测"读取结果在对应文件被写之前不遮蔽"的保护规则。
- **次要指标（只描述，不参与判定）**：第一次编辑的请求号、工具调用总数、原文仍可见时的重复读比例、解出率。
- **提示时机**：如果以后还要做，只在 8945 这类"读了很久但没动手"的题上做定向重复。在那之前写好阈值，例如"提示后 3 次请求内开始编辑的比例，M 比 N 高至少 50 个百分点"。本轮不建议付费。

## 7. 局限

- 是否重复，只看参数推断出的行范围和搜索模式，不比较输出内容。搜索要求模式完全相同，近似模式和换了顺序的备选项不算，所以重复读偏低估。
- 写入识别靠命令解析。运行代码的命令只视为改动工作区外和构建目录；如果它改了仓库源码而没有可识别的路径，会漏掉，那次重读就会被误算成重复读。留出样本里没有遇到。
- 遮蔽从第 3–4 步开始，几乎所有重复读都发生在遮蔽开始之后，没有"不遮蔽"的对照。间隔分布在第 5 档的骤增是强烈的描述性证据，但还不是因果证据，要靠第 6 节的实验来确认。
- 和解出的关系只是相关，而且受运行长度影响很大；只看前 15 次调用时又会丢掉短运行。
- 人工核对只有一名核对者，没有盲法；留出样本 56 条，误报率上界约 11%，漏报率上界约 21%。
- P4 只有 6 道题、53 次运行，每格 2–3 次；通过只出现在 2 道题上。P4 的 `read_file` 每次最多返回 100 行，翻页方式和其他实验不同。
- A6-R 本身是 A5 失败题的重试，题目更难，和 A5、CR-2 的占比不能直接比较。

## 8. 复现

需要 `runs/` 和本地产物目录（`<artifacts>`，脚本里的 `ARTIFACTS` 常量）下的原始产物，只读打开；两者都不入库。

```text
python scripts/analysis/reread/reread.py --workers 6     # 全部运行；写 out/reread_runs.json、out/reread_summary.json 和 .tmp/reread/calls.jsonl
python scripts/analysis/reread/prompt_timing.py           # 写 out/prompt_timing.json

python scripts/analysis/reread/sample.py score tuning
python -m pytest scripts/analysis/reread/test_reads.py -q
```

`sample.py draw <tuning|holdout>` 用固定种子从 `.tmp/reread/calls.jsonl` 重新抽样。调参样本是用第一版规则抽的，用现在的规则重抽，得到的条目会不同；已提交的样本文件才是核对时实际用的。
