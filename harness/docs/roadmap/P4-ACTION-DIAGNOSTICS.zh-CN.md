## 3. 请求重建的限制与追加校准

首批准备脚本使用排序后的 JSON 保存请求。它保留工具语义，却改变了工厂生成的工具对象键及参数排列顺序；例如 `search_replace` 的参数从 `path, search, replace` 变成 `path, replace, search`。这个变化为两组共同持有，不改变批内声明的干预差异，但首批控制请求不能称为历史 HTTP 字节的精确复刻。

供应商输入计数也有一个可核对的差异：历史 M8/T23 分别为 5688/11928 tokens，首批对应控制为 5690/11930。尚不能仅凭多出的两个 token 认定排序造成历史动作不复现，也不能全部归因于模型随机性。

发现这一点后，单独冻结 `native-tools/` 的 T23 校准：保留工厂生成的整个工具 schema 顺序，有/无倒计时各 3 次，AB / BA / AB。首批证据不修改；新增请求的消息与其他参数保持一致，仍只取单步响应。原始 HTTP 未存档，因此校准也只声称恢复已知工具顺序。

校准的 6 条响应仍均为读取，参数有效：保留提示组 2 次查询 HTML 的 `get_outdated_docs`、1 次读取 viewcode 第 60–80 行；去掉提示组 3 次均读取 viewcode 第 60–80 行。两组修改/测试/完成均为 0/3，没有候选，不启动回放或验收。

其中 4 次请求重读的 viewcode 第 60–80 行，已经包含在历史第 22 次读取的第 1–80 行里，且该正文在当前输入中仍完整可见。因此，本轮也观察到了“正文可见却仍重读”的情况，不能只用被遮蔽或遗忘解释全部重读。它可能涉及关注重点、核对或行动选择，本轮无法区分，更不能直接推断模型是否理解了修复点。

保留提示组的输入计数恢复为 11928，与历史该请求一致；去掉提示组为 11920。这检查了一个已知重建差异，但计数相同仍不证明历史 HTTP 字节相同。恢复已知工具顺序后也未稳定重现历史修改，因此不能据此前两次末尾修改，把倒计时猜测当成确定原因。

本轮在 18 次后结束，不增加样本直到出现预期动作。下一步若继续，应另定一个短续跑问题，检查保留原文带来的读取变化是否能转化为更早的有效修改；当前结果不支持直接增加工作记录或复杂记忆模块，也不能据此归结为模型一般能力不足。
