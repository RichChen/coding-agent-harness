# CR-2 结果：把冻结的检索接进 agent

日期：2026-10-29。依据：CR-2 合同第 4 节、7.3、第 10 节，[CR-2-FREEZE](CR-2-FREEZE.md)，AUDIT-CR-2c。数据：`docs/retrieval/cr2-runs.json`（sha256 `bb6171cf…`），分析输出 `docs/retrieval/cr2-analysis.json`（sha256 `f592dcc5…`），分析脚本为 r4 的 `scripts/analyze_cr2.py`（提交 `fcfea74`）。

## 结论

- **主指标（首次触碰 gold 文件的步数）**：P − N 为 −0.02 步，95% 区间 [−1.87, 2.05]；T − N 为 +0.10 步，区间 [−0.97, 1.34]。两项都**未检出差异**。
- **T 组 280 次运行没有一次调用 `retrieve_code`。** 工具在每次运行的 schema 里都有，模型一次也没有用。所以 T − N 比较的只是“工具列表里多一个不被使用的工具”，没有测到通过工具检索的效果。
- O − N 为 −2.42 步，区间 [−3.85, −1.14]，O 组更早触碰 gold 文件。O 组是给出正确文件的上限参照，不是检索方法；这个结果只说明注入生效了（合同 7.3）。
- 修复率（次要指标，只描述）：P − N +2.9 个百分点 [−3.2, 9.6]，T − N −0.7 [−5.4, 3.9]，O − N +2.1 [−5.4, 9.6]，三项都未检出差异。
- 4 项预先写定的敏感性分析（S1–S4）里，上面各项区间是否跨 0 都没有变化。点估计的正负号有几处变化，见第 7 节。

负数表示更早或更少。所有区间都是按题 bootstrap 95% 区间（10000 次，种子 20261026）。每道题先对 5 次重复取平均，再按题配对；56 道题，四组各 280 次运行。

核实：280 次运行的 `agent-tools.json` 都含 `retrieve_code`（注入核对也逐槽位检查过）；`events.jsonl` 里没有一条 `retrieve_code` 的 `tool.intent`；`retrieval-calls.jsonl` 全部为空；159 次退役运行里的 T 组运行也没有调用。T 组用到的工具是 `run_command` 5134 次、`read_file` 3084 次、`search_code` 1130 次、`search_replace` 322 次、`list_dir` 56 次、`write_file` 13 次、`edit_file` 11 次。CR-2b 的 2 个 canary T 槽位也没有调用。

所以本轮 T 组的结果不能说明“agent 自己调用检索工具”有没有用：模型在 b0-v2 的 system prompt 和这份工具描述下不选择这个工具。这是 CR-2 结论的一部分。

## 9. 运行质量

- **槽位**：1120 / 1120 都有最终运行，runner 没有停止（`halt_reason` 为 null）。
- **注入核对**：运行中通过 1114 个；6 个 `infra_kept` 用同一个冻结函数离线核对，也通过。
- **harness 工具错误**：全部 1279 次运行（1120 个最终运行加 159 次退役运行）都是 0。
- **退役重跑 159 次**，按原因：

| 原因 | 次数 |
|---|---|
| 模型服务商网络失败（`provider network`） | 103 |
| 候选快照前容器消失（`container_gone_before_snapshot`） | 25 |
| 容器清理失败 | 24 |
| 候选快照 Docker 重试 3 次后失败 | 3 |
| 容器启动失败 | 1 |
| grader 在测试执行前失败 | 1 |
| 上一轮 `12585/n/r4` 的两次退役（r3 以后属于 `delta_too_large` 一类） | 2 |

- **`delta_too_large`**：12 个槽位（N 5、P 1、T 3、O 3），其中 11 个在 `scikit-learn__scikit-learn-12585`，1 个是 `scikit-learn__scikit-learn-10908/t/r4`。原因是 agent 跑仓库测试时重新生成了 Cython 源文件（9.1 重放）。
- **`delta_lost`**：2 个，都在 T 组（`pytest-dev__pytest-7490/t/r1`、`sympy__sympy-17655/t/r4`）：用过编辑工具，但最终改动为空。属于任务结果。
- **`infra_kept`**：6 个，见第 6 节。它们的三次运行里都出现过模型服务商网络失败，退役次数用完后按冻结规则保留；都跑满了 40 次模型调用，status 是正常的 fail 或 partial。
- **墙钟时间**：续跑 42 小时 46 分（10-27 12:21 至 10-29 07:07），估算是约 23 小时。多出来的时间主要来自 159 次退役重跑（占全部运行的 14%）和大量模型调用的网络重试。
- **退役重跑对长运行的偏向**（AUDIT-CR-2c 第 2 节第 4 条）：网络失败按模型调用发生，长运行更容易被退役重跑。S4 改用每个槽位第一次不是 `infra_error` 的运行，结论没有变化（第 7 节）。
