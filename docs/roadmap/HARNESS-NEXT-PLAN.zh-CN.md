# Harness 下一阶段：阶段拆解与验收方案

日期：2026-10-30。状态：供作者审阅的具体方案，尚未开始实施。

先读 [改进纲领](HARNESS-NEXT-CHARTER.zh-CN.md)。本文描述建议的模块、依赖、交付和验收；新增文件名、状态名与规模均为提案，不代表现有 API，也不是逐任务执行合同。

## 1. 阅读顺序与总体安排

时间有限时先读第 2 节的用户流程、第 6 节的阶段表、第 8 节的协作方式和第 11 节的待讨论项。接口与容易出错的细节放在第 3–5 节。

建议工作顺序：

```text
P0：检查已有轨迹、选定适用场景
                ↓
P1：确定工作区版本、验证记录、完成状态等共用接口
                ↓
        ┌───────┼────────┐
        ↓       ↓        ↓
 P2-A 工作区索引  P2-B 验证服务  P2-C 独立验收用例
        └───────┼────────┘
                ↓
P3：串行接入入口、完成检查与会话恢复
                ↓
P4：真实使用、同期小对照、演示和交付
                ↓
再讨论：扩大评测 / 生成测试 / 经验沉淀
```

P2 的并行是开发工作并行，不增加产品运行时的 agent 数量。B 的验证服务不依赖 A 的向量检索完成；共用的是工作区版本信息。A 功能若出现阻塞，不应让 B 的独立验证用例停工。

## 2. 第一版用户流程

### 2.1 输入、操作和输出

用户提供：公开问题描述、仓库及初始版本、执行环境、公开测试命令与总预算。第一版不负责自动发现所有项目的安装方式。

建议提供一个薄的普通任务入口，暂名 `scripts/run_workspace.py`，复用现有配置、factory 和 RunSession。既有 `run_single.py` 与 SWE 实验入口保留原默认行为。最终是否合并入口在 P1 确定，避免复制整套 runner。

| 步骤 | 系统动作 | 作者能够检查的东西 |
| --- | --- | --- |
| 1. 准备 | 校验环境、建立初始工作区版本，执行声明的基线验证 | 起始文件清单、环境标识、原本的测试失败 |
| 2. 检索 | 对源码及公开测试建立索引，查询相关实现 | 查询、候选位置、文件哈希、索引版本 |
| 3. 修复 | 继续使用现有读写与命令工具 | 工具观察、修改内容、模型及预算记录 |
| 4. 更新 | 下次检索时检查实际工作区变化 | 新增、修改、删除文件及缓存复用情况 |
| 5. 验证 | 对当前候选快照执行冻结的开发验证 | 验证针对的版本、命令、结果与完整日志 |
| 6. 反馈 | 行为失败时返回有界摘要，允许有限次修改 | 每轮失败原因、后续修改、停止原因 |
| 7. 交付 | 导出补丁及对应的最终验证状态 | 补丁、报告、运行轨迹、未覆盖范围 |

示例：某 Python 仓库的重试次数处理错误。第一次修改通过目标检查但破坏了一个原本通过的回归用例；B 反馈该失败，第二次修改通过声明的检查。A 在两次修改之间返回相应版本的源码位置。这是演示场景描述，不是已经完成的真实案例。

### 2.2 对外输出必须区分三个判断

- **运行状态：** agent 正常结束、预算耗尽、取消、执行故障等。
- **开发验证：** 指定检查通过、行为失败、无法判定、尚未执行；另附覆盖范围。
- **任务解出：** 有独立评测时由独立评测给出；普通本地使用没有该证据时标为未知。

例如可以输出“运行结束；回归检查通过；目标行为尚未独立验证”。不能将这三个字段合并成一个模糊的 Success。

建议新增的职责边界：

- `src/retrieval/workspace.py`：工作区语料、变化检测、索引版本；不负责结束 agent。
- `src/validation/`：公开验证配置、候选版本、执行结果、日志与基线比较；不导入隐藏 grader spec。
- 一处运行控制组件：判断是否可结束、如何继续、何时耗尽预算。放在哪里由 P1 确定，不要求大规模重构 loop。
- 一个运行检查入口：汇总候选修改、检索和验证记录。优先复用现有 trace/artifact，避免再做一套全量日志系统。

已有 summary、masking、候选错误分类、命令状态和恢复能力不重新包装成新增功能。新工作需要填补的是它们之间缺少的关联和控制规则。

## 4. A：工作区检索的具体设计

### 4.1 两种代码来源并存

冻结模式继续接受 `repo + base_commit`，使用原语料、参数和缓存。工作区模式接受受控文件视图，包括文件路径、字节内容与版本清单。

本地调试读取指定目录；Docker 运行从实际容器工作区获取受控快照。不能用一个宿主目录替身假设它与容器一致，也不能让检索工具获得任意宿主文件访问权。

建议共用的版本描述包含：起始源码版本、纳入范围的文件内容哈希、增删记录、规则版本。文件时间戳可以用于加速，但不能作为唯一正确性依据。

### 4.2 第一版的更新过程

1. 在查询边界检查受支持文件集合，识别新增、修改、删除和重命名。
2. 将这次查询绑定到一个稳定快照，不能混合更新前后的索引。
3. 变化文件重新切块；只有实际编码输入和模型/预处理配置相同，才复用向量。
4. 删除文件撤销旧索引项；重命名可先按删除加新增处理。
5. 初版允许重建小仓库的 BM25 统计；不能简单把新增排名接到旧排名后面。
6. 更新完成后发布新的索引版本；失败时明确返回不可用或过期状态，不把旧索引声称为当前版本。

常规文件工具以外，`run_command` 也可能修改代码，因此不能只监听 `edit_file`。第一版采用查询边界扫描和串行修改/查询；文件监听、异步流水线、base+overlay 等优化延后。

查询得到的是查询时刻的快照。后续若文件已改变，读取前可以检测并提示重查；不能承诺一个返回结果永远与未来的工作区一致。

### 4.3 语料与返回内容

初版新语料限定为 Python 源码及公开测试。排除 `.git`、虚拟环境、缓存、构建产物和声明范围外的文件；符号链接、超大文件等按明确规则拒绝或跳过并记录。

返回路径、符号、行号、材料类型、文件内容哈希、索引版本。第一版继续通过已有读文件工具取正文，不强制增加长代码片段。

已有 CR 向量可能只能覆盖固定提交内容。工作区的新文本需要实际编码；CPU/GPU、模型下载及磁盘缓存要有明确预检。无可用 encoder 时应报错，或在用户显式选择下用标记清楚的 BM25 模式；禁止静默退化后仍称 hybrid。

### 4.4 A 的验收证据

至少覆盖新增、修改、删除、重命名、通过命令修改、行号移动、无变化重查，以及查询期间版本稳定性。

演示必须让作者看到：修改前后的结果确实不同，删除文件不再出现，缓存复用与重新编码的数量可解释。机制用例可以采用固定 encoder；另外需要真实本地 encoder 的小范围检查，二者分开标注。

若提取冻结实现的公共部分，使用既有缓存和明确查询清单检查旧排序兼容。这是兼容性验证，不用于再调 CR 的 test 参数。

## 5. B：验证与反馈的具体设计

### 5.1 验证材料由谁提供

第一版由作者/仓库配置声明公开验证命令、测试材料、环境及覆盖范围。优先支持已经能跑通的 Python/pytest 仓库；不默认让模型自行安装任意依赖或生成测试。

启动时固定本次验证所用的测试与配置，并先跑基线。如果基线已经失败，区分目标失败、其他已知失败和无法运行；未分类的失败不能靠忽略来换取绿色状态。

对模型来说，公开测试内容可读；对最终验收来说，不能由候选补丁随意删除断言、改成 skip 或改测试配置来获得通过。新提交的测试可以作为候选产物保存，但不自动取代本次声明的检查。

只有回归测试时，验收说明写“已通过指定回归检查”。若另有来自公开需求的目标行为检查，需明确其来源、预期及冻结时间，再报告目标检查结果。

### 5.2 一次验证记录包含什么

下表为概念字段，不预先锁死序列化 API。

| 字段组 | 需要回答的问题 |
| --- | --- |
| 候选身份 | 起始版本是什么，哪些执行相关文件发生增删改，最终内容的哈希是什么？ |
| 检查身份 | 使用哪个测试集合、命令、工作目录、结果解析规则和验证策略版本？ |
| 环境身份 | 哪个镜像/解释器/依赖环境及允许的环境参数？不写入密钥明文 |
| 结果 | 通过、行为失败、无法判定、未执行；基线比较；收集/执行/跳过测试数量 |
| 证据 | 退出状态、原始输出产物、有限长度反馈、开始结束时间 |
| 控制信息 | 本轮编号、剩余预算、操作 ID、当前验证是否已被后续修改作废 |

候选身份不能只哈希被编辑的 `.py` 文件。配置、依赖声明等可能改变运行结果，必须纳入支持范围或明确禁止该类修改。哈希算法、路径规范和排除规则也要有版本。

测试集合、环境或命令变化同样使旧通过凭据失效。索引版本是检索时刻的语料描述，不直接冒充完整候选版本。

### 5.3 验证在哪里运行

推荐对当前候选快照创建独立的临时验证工作区，复用已准备的环境和受控执行后端。验证产生的缓存、文件和副作用不回灌主编辑工作区；每次测试结束记录清理状态。

主要新增工作是：运行中可靠取出候选、准备验证副本、应用冻结测试配置并收集结果。已有 `export_delta` 是入口，不代表任意后端已经具备完整实现；P1 先核实支持范围和导出限制。

隐藏 grader 始终在另一条路径。不能把其 F2P/P2P 列表、test patch、gold patch 或诊断作为修复反馈。项目自身的单元测试中可以使用人为构造的失败用例验证机制，但必须标明 fixture，不能把它当成真实修复增益。

### 5.4 怎样接入循环

建议模型可调用一个显式验证动作，暂名 `validate_patch`；主循环在准备结束时还执行同一套完成检查，防止模型绕过该动作直接终止。

```text
模型请求验证 / 模型准备结束
              ↓
获取当前候选版本
              ↓
存在同候选、同检查、同环境的完整有效记录？
       ├─ 是：读取记录
       └─ 否：在预算内执行验证
              ↓
通过指定检查 → 允许以准确状态结束
行为失败     → 有剩余反馈预算则继续修改，否则结束并保留失败
无法判定     → 按已声明规则停止或有限处理，不能假装行为失败/通过
```

仅靠 system prompt、`after_tools` 或新增工具 schema 不能保证完成规则。需要在当前无 tool call 的结束分支进入 DONE、关闭工作区之前处理。

自动验证不产生伪造的模型 tool-call ID；采用真实宿主操作记录，并以明确标注来源的观察反馈给模型。主动工具调用和自动完成检查共用验证服务、预算和结果缓存。

建议初版每个任务最多 3 次候选验证；最多 2 次失败反馈后继续修复机会。启动前的基线验证单独计数，但仍计入总时间/计算成本。这些是待确认默认值，不是已经授权的付费运行额度。

验证通过后，若模型或命令再次改变候选，必须重新验证。缺乏足够预算时输出未验证/未解决，不为得到绿色状态不断追加调用。

### 5.5 结果判定与恢复

不能单凭退出码 0 判定有意义的通过：零测试、全跳过、收集异常、部分中断必须单独处理。超时可能是补丁卡住，也可能是环境问题；证据不足时标为无法判定，不机械归因。

保存验证意图、执行结果及完成控制状态。恢复时：

- 已提交且身份完全匹配的结果可以复用；候选变更后不可复用。
- 已启动但结果未知的验证，先确认进程/容器状态与清理结果。
- 只有在明确允许、清理完成并能创建全新验证环境时才进行受限重跑；不能把测试笼统标成只读操作。
- 验证记录落盘后、最终完成标记之前崩溃，不应重复调用模型或重复消耗已结算的验证预算。
- 使用现有 session 的通用恢复设施；新增控制状态仍需专门接线和检查，不能只写 JSON 就声称可恢复。

## 6. 阶段交付与验收

### P0：先确认 B 可以介入哪些真实问题

**输入：**已有 A5/A6/CR 的公开轨迹、候选修改和运行摘要。

**工作：**按固定规则选择约 12–20 条轨迹，覆盖至少两个仓库和不同结束原因，包含少量成功记录作参照。人工核对是否存在未验证就提交、验证后继续编辑、明确失败未处理、环境错误混淆等情况。已有日志无法绑定代码版本时标记未知，不用命令字符串猜测出确定结论。

**交付：**一张带运行路径和证据位置的诊断表；1–2 个首批受支持仓库及其公开测试/环境说明；明确哪些失败 B 可以介入、哪些主要受模型能力或环境限制。

**验收：**作者能从表中打开至少两条完整轨迹理解设计动机。比例只描述该样本，不能推广为全项目失败分布。

**转向条件：**如果几乎没有可介入问题，缩小 B 的收益预期，保留验证可信度与使用性目标；不要凭空编造“主要瓶颈”。这一判断在扩大实施前与作者讨论。

### P1：确定共用接口和受支持环境

**工作：**由一个负责人确定工作区版本表达、候选导出方式、验证记录、结束状态、预算与恢复行为。检查新入口如何使用已有 Docker 后端；给 A/B 提供相同的极小示例数据。

**交付：**接口说明及两个端到端序列图/样例：成功结束、失败反馈后继续。将决定追加到本方案或一个阶段报告，避免为每个小任务生成新计划文件。

**验收：**检索和验证实现者可以依据共同输入独立开发；旧入口默认行为、隐藏评分边界和未来集成点明确。复杂接口问题在此串行解决。

### P2-A：工作区索引实现，可与 P2-B 并行

**工作：**通用检索能力提取、工作区来源、源码/测试语料规则、变化检查、缓存和结果版本。正常入口接线暂交给集成人。

**交付：**能对指定受支持工作区独立构建、查询、更新的模块；修改前后演示记录。

**验收：**第 4.4 节的更新场景通过；原冻结检索的兼容检查通过；真实 encoder 小检查可运行且缓存目录/设备不依赖作者机器上的硬编码路径。

### P2-B：验证服务实现，可与 P2-A 并行

**工作：**声明验证配置、运行基线、候选快照验证、结构化结果、覆盖范围、日志及预算计数。先在 agent 循环外调用服务。

**交付：**对两版候选分别产生可核查记录，能区分行为失败、环境问题和无有效测试。

**验收：**候选修改使旧记录失效；修改测试或 skip 不能绕过固定检查；验证副作用不污染编辑工作区；完整日志可追踪。

### P2-C：独立验收用例与检查工具，可并行

**工作：**根据 P1 的行为约定构造小仓库 fixture 和异常场景；设计一条运行的阅读顺序。该角色不修改 A/B 内部实现来配合测试。

**交付：**只围绕关键行为的测试和演示素材，涵盖版本过期、零测试、预算用完、中断恢复、命令修改文件等。

**验收：**测试可以发现实际错误，而不是复制实现判断。fixture 与真实模型结果分开。

### P3：串行集成入口、完成检查与恢复

**工作：**一个负责人统一修改 factory、配置、loop、session 和入口。接通 A/B，增加准确的报告状态，保持旧配置默认关闭新行为。

**交付：**完整的“检索—修改—验证—反馈—结束”运行；可以定位每版补丁与对应验证。

**验收：**先用确定的模型响应序列和真实受控执行环境检查：通过、失败后修复、无测试、无法判定、预算耗尽、取消、重复结束、关键崩溃窗口。旧行为受影响的现有测试通过；必要时运行仓库要求的完整公开测试，说明环境依赖。

新增测试通过不能代替旧行为兼容。新模式关闭时不应新增检索、模型调用或验证执行。新模式在恢复时不能绕过完成规则或重复结算。

### P4：真实使用、效果检查与交付

**工作：**先运行少量开发任务检查工具是否真正被使用、反馈是否可读、环境是否稳定；修正接线问题后，再决定是否进入第 7 节的冻结小对照。

**交付：**一条可重复启动的使用路径、一条真实成功或清楚失败的完整轨迹、一个机器生成的报告、使用说明和准确的项目介绍草稿。

**验收：**作者能自行启动、找到输出、解释一次验证失败、确认最终补丁版本；真实运行的费用和限制有记录。只有完成新证据核验后，才讨论更新简历措辞。

## 7. 如何检查收益，避免再做一轮解释不清的实验

### 7.1 分开回答三类问题

| 问题 | 合适的证据 |
| --- | --- |
| 机制有没有正确实现？ | 固定输入和失败注入：索引一致性、结果失效、完成控制、恢复与预算 |
| 使用起来是否方便？ | 明确环境下的启动步骤、完整运行、失败定位、产物查找 |
| 是否提高修复能力或效率？ | 同期、预算可比的真实任务对照及独立判分 |

A 报告冷启动/更新/查询时间、编码次数与缓存复用、版本正确性；实测什么报告什么。新语料的相关性效果单独评估，旧 CR Hit@5 不直接搬过来。

B 报告最终候选验证覆盖、反馈次数、无有效测试/环境失败比例、总时间和模型成本。开启 gate 后验证覆盖自然提高，这是功能结果，不是修复率因果增益。

### 7.2 建议的小对照

先用 4–6 个公开开发任务调通流程。冻结后可用另一个预先声明的 8–12 题小集合、每组 2 次作可行性检查，具体题量依运行成本调整。此规模不承担“证明小幅稳定提升”的任务。

初次比较聚焦 B：两组采用同一 A、模型、公开验证材料、工具与提示，只改变强制完成检查/反馈策略。两组都可主动调用验证工具，避免把工具可用性变化混进 gate 的作用。

- 基线：沿用自然结束策略，可以自发验证。
- 新策略：结束时检查当前候选验证状态，按固定预算反馈。

两组的模型调用、token、总时限、测试次数等上限应在运行前对齐；实际消耗也要报告。验证与反馈消耗不能免费附加到新组。最终补丁由同一独立程序判分，判分结果不回传运行中的求解过程。

按任务成对、随机交错运行，记录请求/返回型号、可得的 fingerprint、时间和参数。API seed 不支持时如实说明，不能称为完全匹配的随机种子对照。发生模型切换时保留运行段并检查影响；不能仅凭别名相同就合并比较。

旧 A5/A6/CR 的题和结果已经被开发过程使用，复用时称开发/回归集；只有确实未用于本轮调参且预先封存的任务才能用于相应的保留检查。按新策略成功与否挑题会使结论失真。

输出逐题结果、配对差与适当区间、成本差、环境异常与所有偏离。小样本未检出差异时保留工程结论。也可因为成本太高而在机制与使用性完成后收尾，不强求立即扩大评测。

## 8. 多智能体协作与模型选择

### 8.1 分工建议

以下为开发助手安排，和 harness 实验中的求解模型是两回事。

| 工作 | 默认候选 | 并行方式 |
| --- | --- | --- |
| P0 轨迹提取与分类 | 6.1 Sol，medium/high | 可与环境清单核查并行，结论人工复核 |
| P1 版本/验证/恢复接口 | Astra medium/high，或 6.1 Sol high/xhigh | 单一负责人；接口讨论不分成多个竞争实现 |
| P2-A 索引模块 | 6.1 Sol high，必要时提高推理强度 | 独立工作树 |
| P2-B 验证服务 | 6.1 Sol high/xhigh | 与 A 并行；快照与副作用难点可由 Astra 协助审查 |
| P2-C 行为测试、报告和使用路径 | 6.1 Sol medium/high | 独立工作树，遵守统一接口 |
| P3 主循环、预算与恢复集成 | Astra medium/high，或已掌握接口的 6.1 Sol high/xhigh | 串行集成，由一个负责人修改共用文件 |
| 独立阶段审查 | Astra medium/high | 在固定提交上读代码和证据；不与实现者同时改文件 |
| 边界清楚的说明、解析和小修正 | 6.1 Sol；独立会话也可选 5.6 Sol | 依据任务表现和实际费用选择，不先假定某型号更省 |

用户允许 Sol 使用不受限的推理强度，具体取值仍受调度接口支持约束；Astra 本轮按用户偏好限制在 low、medium、high。高推理强度不是所有任务的默认值；相同问题反复失败时，先修正上下文/验收定义，再决定提高强度或换模型。

2026-10-30 补充核查：**子智能体接口与桌面新会话接口的模型列表不同。** 子智能体列表未列出 `gpt-5.6-sol`；桌面的 `create_thread` 和 `send_message_to_thread` 在当前主机列出了 `gpt-6.1-sol`、`gpt-5.6-sol`、`gpt-6-astra`，并支持相应推理强度。因此独立会话可以把 5.6 Sol 列为可选型号；此前“待确认”的说法仅适用于尚未核查桌面接口时。工具实际创建仍会校验可用性，目前尚未启动这些实施会话。

上述分工是项目判断，不是官方对本仓库的性能保证。当前官方参考：[模型选择](https://developers.openai.com/api/docs/guides/model-selection)、[6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)。不将 API 标价直接当成桌面额度或第三方渠道费用。

### 8.2 会话与代码所有权

作者已允许实施时显式创建与本仓库关联的独立会话，并希望直接查看任务分派。桌面项目列表已确认存在 `coding-harness`，路径为 `D:/crq/src/coding-harness`，且为 Git 仓库。优先让 A、B 等主要交付使用可见会话；短小核查由主会话处理，确有收益时才用临时子智能体。初始任务与后续指令会显示在对应会话中，由主会话读取结果、跟进与集成。本次核查没有启动实施任务。

每个写代码的任务使用独立 worktree 和 `codex/` 前缀分支，共用同一接口基点。关联同一项目不要求共用一个可写目录。初期建议最多两个实现会话同时工作，验收/审查按需要启动；子智能体并发槽位不能直接当成桌面会话的并发限制。GPU、Docker 和付费调用由主会话统一调度。

| 区域 | 所有权 |
| --- | --- |
| 工作区检索模块及其局部测试 | A 实现者 |
| 验证服务及其局部测试 | B 实现者 |
| 独立行为用例、运行检查展示 | 验收实现者；避免与前两者写同一测试文件 |
| factory、config、loop、session、普通入口 | 集成人单独修改 |
| 冻结实验文件、历史结果、隐藏 grader | 不作为普通功能任务的修改区域 |

主会话先合入共享接口，再依次集成 A/B/验收改动，最后处理完成控制。接口变化由集成人统一更新并通知各会话，不能靠最后合并时猜语义。

每次交接给出：基点、允许修改范围、接口版本、完成的行为、验证证据和未解决问题。阶段审查针对代码与运行产物；一个智能体自称“完成”不等于验收通过。常规修复由负责人继续处理，作者主要审阅阶段结果和范围变化，不逐条批准文件编辑。

### 8.3 控制独立会话的额外开销

新建可见会话的目的，是让任务边界与过程可见。不能承诺它与内部子智能体有完全相同的费用；实际消耗受模型、上下文、推理、工具使用和缓存影响，参见 [官方用量说明](https://learn.chatgpt.com/docs/pricing)。

- 使用新会话加简短交接，默认不 fork 整段长对话。只给任务目标、相关方案章节、代码入口、修改范围和验收条件，避免每个角色重新做全项目调研。
- 一项完整模块工作使用一个会话，后续局部修正继续该会话；不为每个文件或每条测试建新会话。
- 主会话使用状态摘要和结果游标跟进，按需读取细节；不反复把多个会话的完整历史互相复制。
- 先跑各自相关的检查，集成后统一做必要的跨模块回归；不让每个会话重复运行整套昂贵实验。
- 模型缓存、已有数据和环境能安全复用时复用；工作区仍保持隔离，避免重复下载与安装造成无效等待。
- 小任务留在主会话；主循环、恢复和接口决策维持单一负责人。并行以减少独立工作的等待为目的，不追求会话数量。

## 9. 工作量、成本与收缩顺序

在现有依赖和至少一个 Docker 环境可用、没有大规模重构的前提下，初步工作量估计：P0 约半天到一天，P1 约一天，P2 并行约 2–4 天，P3 约 2–3 天，P4 约 1–2 天。整体约 7–11 个有效开发日；这是包含联调和作者检查的估计，不是模型生成代码的耗时承诺。环境准备或恢复缺陷可能扩大工期，P1 后再估一次。

开发助手费用、本地 embedding 计算、真实任务模型费用分开记录。前期优先离线和 mock；真实模型小检查的单次成本、重试上限和总预算在 P4 开始前具体化。本文未设定或授权新的付费额度。

若工期扩大，依次收缩：后台索引优化、多语言/文档语料、MCP/API、大规模对照。保留工作区版本正确性、候选与验证绑定、有限反馈和完整使用路径。避免最后留下大量模块，却没有一条可运行的端到端流程。

## 10. 完成后可以怎样介绍项目

需要实际完成并验收后，才可使用下面的能力表述：

- 将离线评测过的代码检索接入实时工作区，支持源码及测试定位、修改检测、缓存复用与结果版本追踪。
- 构建候选补丁与开发验证绑定的修复流程，区分行为失败、环境问题和无有效测试，支持有预算的反馈与恢复。
- 保留 A5/A6/CR 的独立实验，说明已有证据支持什么、哪些改进仍未证明修复收益。

不能提前写“修复率提升”“生产级”“全自动适配任意仓库”“实现自主进化”。若只有机制演示，明确称演示；若小对照无显著收益，项目介绍仍可陈述已验证的工程行为。
