# Harness 下一阶段改进纲领：工作区检索与修复验证

日期：2026-10-30。状态：讨论稿，记录已认可的方向，供作者审阅后继续讨论。

配套文件：[阶段拆解与验收方案](HARNESS-NEXT-PLAN.zh-CN.md)。本轮只新增方案文档，不代表功能已经实现或新实验已经启动。

## 1. 要达到什么目标

在现有 Coding Agent Harness 上，补齐两项相互配合的能力：

- **A：工作区代码检索。** 将已经评测过的检索模块接入正常任务入口，使其能够反映正在编辑的仓库状态，并说明结果来自哪个版本。
- **B：修复验证闭环。** 将测试执行、候选补丁和完成状态关联起来，让明确的验证失败能够驱动有限次继续修复，最终交付补丁及对应的验证记录。

近期采用 **A 的必要接入 + B 的验证主线**。系统仍以现有模型调用循环、工具、执行隔离、上下文管理和独立评测为基础。B 会扩展完成控制逻辑，但不要求重写整个 agent。

目标是增强实际任务能力、降低使用门槛，并形成作者能演示和讲清楚的工程成果。工程交付不以修复率一定上升为前提；收益结论必须另有对照证据。

## 3. 研究与设计依据

VibeMemBench 将“存在对目标有帮助的经验”和“记忆系统能否交付有用上下文”分开研究，并采用参考设置下的收益筛选。因此它与 A5 相关，但不是对 A5 的直接复现或背书。尤其要区分：**源任务修复成功，不等于经验对新任务有用。** 参见 [论文 §3–5](https://arxiv.org/html/2609.23570v1)。

这对后续设计的启发是：保留经验来源、代码版本和行为证据，逐步识别失效环节。不能因为检索命中或一次测试通过，就自动把条目标记为可迁移的有效记忆。

工程实现继续遵循仓库 [AGENTS.md](../../AGENTS.md) 指定的参考项目 `D:/crq/src/learn-claude-code-main`。本次已参考其 `docs/zh/s01-the-agent-loop.md` 和 `s12-worktree-task-isolation.md`：围绕循环补机制，并将并行开发的工作区隔离。教程是结构参考，不替代本项目的执行边界与恢复要求。

## 4. 第一版交付的样子

作者能从一条明确命令启动一个受支持的 Python 仓库任务，并沿下面的流程检查输入、输出和版本：

```text
公开问题 + 仓库配置
        ↓
检索当前工作区的实现与测试位置（A）
        ↓
读取、修改、形成候选补丁
        ↓
在明确环境中运行事先声明的开发验证（B）
        ↓
通过指定检查 / 反馈失败继续修复 / 无法判定或预算耗尽
        ↓
导出最终补丁、对应验证记录、运行轨迹与限制
```

第一版建议范围：

1. 支持少量明确配置的 Python 仓库；验证首先支持 pytest。执行环境沿用已有可准备的环境，优先让 Docker 路径端到端成立。
2. 检索覆盖源码与公开测试，查询时检查变化；更新一致性优先于后台监听和高性能增量索引。
3. 采用已有测试；记录其覆盖范围。只有回归测试时，输出“回归检查通过”，不宣称目标行为已解决。
4. 为当前候选版本生成验证记录；失败后有限次反馈，不每改一行就触发测试。
5. 同时提供无模型调用的机制演示和少量真实任务检查；分别报告二者能证明什么。
6. 有清晰的使用说明：启动、查看一次轨迹、定位一次失败、找到最终补丁和验证结果。

## 6. 必须保持的系统约束

1. **历史证据有版本。** 不覆盖旧配置、冻结清单、报告和运行产物；共享代码必要变动需验证旧入口兼容。新模式新增语料或控制规则后单独命名与记录。
2. **工作区来源一致。** 本地模式读取明确授权目录；Docker 模式读取实际容器工作区的受控快照。索引不扫描宿主机 grader 私有目录。
3. **验证对应具体产物。** 候选内容、测试配置或环境发生变化，旧记录不得被自动当成当前版本的通过凭据。
4. **开发验证与独立评分分开。** 运行中只使用公开、正常开发可见的测试材料。SWE 隐藏测试、gold patch 和独立 grader 的隐藏诊断不反馈给求解过程。
5. **状态含义清晰。** agent 结束、指定检查通过、独立评测解出，是三个不同判断。无测试、全跳过、环境失败和超时不能伪装成通过。
6. **预算与恢复受控。** 反馈轮次计入总预算；不会每轮重新获得整套调用额度。崩溃后的未知执行状态不得直接记为通过或盲目重跑。
7. **结论不跨实验条件。** 新旧模型别名相同也不代表版本相同；新收益采用同期对照。工程正确性与修复效果分别报告。

## 7. 保留记忆方向的方法

后续可以由 B 产生带版本与验证证据的修复记录，将它们提炼成候选经验，再在其他任务上验证是否值得注入。候选记录应带适用条件、来源与失败边界。

这一步是可选的第二阶段。A+B 完成不等于经验库已经能自我改进，也不自动支持“RSI 已实现”的表述。
