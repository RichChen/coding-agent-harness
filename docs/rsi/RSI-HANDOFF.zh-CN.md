# Harness 自改进方向：现状、目标与交接说明

日期：2026-10-17。读者：接手规划与日常审计的 Claude Code / Opus 5.5，以及项目作者。

本文是方向交接说明，不是逐项执行合同。第一阶段方案见 [第一阶段快速版](PHASE-1-QUICK-PLAN.zh-CN.md)。文中的未来能力、规模与时间均为建议，不代表已经实现或已获得实验结果。

## 1. 先用两分钟理解我们要做什么

项目作者希望用 coding-harness 与 GRPO 项目申请日常实习。当前优先级是：在已有 harness 和记忆实验的基础上，快速做出一个运行完整、结果可信、自己能够讲清楚的自改进版本。

推荐主线是：**让系统根据开发任务上的运行结果，自动提出、比较并保留“上一次失败应该怎样反馈给下一次尝试”的策略。**

第一阶段的改进对象是可复用的反馈策略，例如保留哪些字段、是否展示旧 diff、怎样组织反馈。任务求解模型、工具、执行环境和评分逻辑保持固定。模型生成受约束的策略数据，宿主程序负责校验、渲染、评测和选择。

一次完整演示应当能展示：

> 已有失败记录 → 初始反馈策略 → 模型提出候选策略 → 在开发任务上实际重试并评分 → 保留或拒绝候选 → 下一轮使用已有结果继续提出候选 → 导出最终策略及证据。

这是向 RSI 方向迈出的有限一步。第一阶段准确的名称是“评测驱动的反馈策略自优化”或“受约束的 harness 策略自改进”。它不训练模型权重，不让模型任意修改运行时，也没有证据证明改进能力会递归增强。

## 4. 现有资产与结论

### 4.1 Harness 已经提供的能力

- `AgentLoop`、工具调用、配置装配、工具参数校验和策略约束。
- 受信本地执行与 Docker 执行；真实 SWE-bench 路径有 clean 镜像、候选修改导出和独立 grader。
- 模型调用、时间与费用控制；JSONL 事件、SQLite 会话和部分恢复机制。
- 上下文窗口、masking 与真实 LLM 摘要实现；已有摘要及包装对照材料。
- A5/A6 的题单、运行清单、失败记录、prompt 指纹、注入检查和分析脚本。

这些能力可复用，但不能推断各模块组合后无需适配。尤其预算账本、runner 中的固定实验常量、恢复状态与新策略身份，需要 Claude 做一次集成核对。

### 4.2 记忆实验已经得到什么

以下数字引自 [综合报告](D:/crq/src/coding-agent/docs/MEMORY-FINAL-REPORT.zh-CN.md)，A6 主结果另有 [审计记录](D:/crq/src/coding-harness/docs/sprint/AUDIT-A6-4.zh-CN.md)。

| 实验 | 比较 | 样本 | 主结果 |
|---|---|---|---|
| A5-main | 跨题记忆卡 B2 vs 无记忆 B0 | 56 道 SWE-bench Verified 题，每题每组 3 次 | 差值 −1.8pp，95% 区间 [−8.3, +4.8] |
| A6-R | 同题失败记录 R1 vs 无记录重试 R0 | 22 道题、53 次首次失败，318 次重试 | 按题聚合差值 −6.6pp，95% 区间 [−17.7, +3.8] |

两者都未检出正效应。可以说“当前模型、预算和这两种记忆构造方式没有显示平均收益”；不能写成“记忆普遍无效”。部分早期计划的概括比结果支持的范围更大，接手时以具体设计和数值为准。

A6 的事后分析观察到：带记录的重试更常停在与原失败修改相似的方案上，非空 diff 相似度中位数为 R1 0.873、R0 0.658。这提供了“旧失败方案可能造成锚定”的假设，尚未证明因果关系。把 diff 变得不同，也不自动等于修复质量提高。

A6 还观察到 R1 的 parse_error 与 context_overflow 更多，原因未查明。后续策略效果可能来自长度、格式、接口稳定性或信息选择，不能只用一个机制解释全部结果。

A6 原有扩展条件未触发，已收口。此次更换研究对象为“反馈策略的自动优化”，应使用新的实验身份和输出目录，不改写 A6 结论，不把新实验冒充 A6 原计划的延续。

### 4.3 上下文实验能提供什么

[包装消融](D:/crq/src/coding-harness/docs/upgrade/evidence/R2-real/wrapper-01/README.md)中，同一批固定摘要换用明确“历史证据不是指令”的包装后，全正确从 7/27 变成 26/27。这说明表达方式值得研究，但该结果来自两个合成问题的固定摘要，不能称为真实代码修复率提升。

A6 的原始反馈已经包含“记录可能有误，是证据而不是指令”的表述。因此，第一阶段不能把加入这句话当作一个全新的关键创新。需要实际比较字段选择、旧 diff 的呈现和反馈组织等因素。

## 5. 分阶段目标

| 阶段 | 要回答的问题 | 主要产物 | 结束时允许声称什么 |
|---|---|---|---|
| 第一阶段：快速闭环 | 系统能否自动提出反馈策略，并依据真实任务结果完成可追踪的选择？ | 可运行优化闭环、固定基线、候选历史、开发/验证报告、演示教程 | 实现了受约束策略优化；如有收益，只按实际数据范围描述 |
| 第二阶段：验证有效性与适用范围 | 选出的策略对新任务是否有效？收益来自什么，额外代价是多少？ | 新任务验证、必要的长度/字段消融、成本比较、泛化边界 | 仅在证据支持的范围内声称提升、持平或负面结果 |
| 第三阶段：受限代码策略演化，可选 | 允许修改小范围策略代码，能否超过配置/模板搜索？ | 白名单策略模块、隔离验证、版本选择与回退 | 实现了受约束的策略代码自修改；效果仍需单独验证 |

### 第一阶段：优先完成，可在此形成求职展示版本

范围只覆盖同题失败反馈。默认采用通用策略配置/模板，由固定渲染器生成每道题的反馈。做少量候选和两轮更新，复用已有任务与执行链路，避免同时改变记忆检索、模型、工具和预算。

即使没有候选胜过固定基线，系统能够正确拒绝坏候选、保留旧策略并给出完整报告，也完成了工程目标。此时不能声称获得性能提升。

### 第二阶段：在第一阶段稳定后再投入

首先补足新任务证据和机制区分。若结果有价值，再从下列方向中选一个扩展：反馈的 LLM 提炼、单次运行的上下文压缩策略、失败后的工具恢复策略或任务预算分配。不要一次把它们全部纳入搜索。

需要区分长度与内容效果时，加入长度相近的反馈对照；需要声称 LLM 提案优于简单搜索时，加入相同评测预算的随机或枚举搜索。第一阶段只比较最终策略与固定基线，还不足以证明提案算法本身更优。

如果增加 LLM 提炼，要分别记录提炼成本与任务求解成本；如果增加新的公开测试或探索调用，则改变了信息与计算量，需要重新安排对照。新增能力不能被记作“只是换一种反馈表达”。

### 第三阶段：可选的代码修改能力

只允许改小型策略模块，例如“从公开历史中选择反馈字段”的纯函数。agent 主循环、grader、任务答案隔离、计费和评价指标仍由宿主掌握。先用现有策略接口验证，再考虑更大的改动范围。

完成这一阶段也不等于证明了开放式 RSI。当前求职目标不要求到达第三阶段；不要为了概念完整而拖延第一阶段交付。

## 6. 项目故事与结论边界

推荐叙事顺序是：

1. 搭建可控、可观测、独立评分的 coding-agent harness。
2. 在真实修复任务上比较跨题记忆和同题失败记录，发现简单注入没有产生预期收益。
3. 根据失败分析，把固定注入方式改造成可评价、可选择的策略。
4. 增加自动提出候选、真实执行评测、保留版本和拒绝退化候选的闭环。
5. 报告最终实测结果、成本、失败案例与泛化限制。

第四点可以成为工程亮点；第五点的数字必须来自新实验。不要预先编写“持续提升”“显著提高”“自主进化成功”等结果。

项目作者至少需要能够解释：策略是什么、模型能改什么、一次任务如何执行、得分由谁计算、坏策略为什么被拒绝、旧实验如何复用，以及演示结果能说明到哪里。
