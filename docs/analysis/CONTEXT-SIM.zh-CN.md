# 遮蔽规则离线模拟：可避免的重复读和输入成本

日期：2026-11-07。在历史轨迹上重放几种遮蔽规则，只读已有运行产物，不调用模型，不启动 Docker。脚本和输出在 `scripts/analysis/context_sim/`，复现方法见第 8 节。判定阈值在预注册提交 `0dd56ba` 里写定，早于任何 B、C、BC、N 结果。

## 结论

1. **规则 A 完全复现。** 1872 个运行、53,976 步，直接调用 `src/runtime/` 现有的遮蔽代码生成的视图，和记录的 `context.prepared` 视图逐条相同；21,069 次重复读的集合和视图状态与重复读分析逐条一致。
2. **只看重复读，放宽遮蔽的效果很大。** 决策组 CR-2 n 里，现行规则 A 下只有 8.2% 的重复读发生时原文还在视图里。改成 B（`keep_recent=8`）后，74.4% 的重复读会看到原文仍在，相当于工具调用的 29.8%；C（读取结果在对应文件被写之前不遮蔽）是 64.5%；BC 是 88.9%；完全不遮蔽（N）是 95.6%。
3. **但按预注册阈值，B、C、BC 都不通过，不建议为其中任何一个付费。** B 的输入只增加 18.1%（中位），但按前缀缓存估算的费用增加 58.2%，没过 T3（≤30%）。C 和 BC 的每次运行输入中位增加 36.9% 和 43.4%，没过 T2（≤30%）；而且各有 72 和 73 个请求超过 96,000 的准入上限，没过 T4。
4. **费用的主要因素是前缀缓存，不是输入总量。** 按窗口滑动的遮蔽，每一步都会把刚滑出窗口的那条结果换成占位符，从那条消息往后的内容都缓存不命中。窗口越宽，每步不命中的部分越长：CR-2 n 里估算的命中占比，A 是 69.5%，B 降到 55.4%，C 是 84.8%，N 是 95.2%。所以 B 输入多 18%，费用却多 58%；C 输入多 37%，费用反而低 5%。
5. **对 REREAD 第 6 节实验设计的影响。** 第 6 节的成本护栏只看输入 token（B 18.1%，能通过），没有考虑缓存。按本文的估算，照原设计跑 B，在按费用计预算的场景里会更贵。如果以后选定某条规则，它的 U（可避免重读占工具调用的比例）是 B 29.8、C 25.8、BC 35.6 个百分点，都不低于 15，所以第 6 节"−10 个百分点"的阈值原则上可达；但本轮没有推荐规则，按预注册不计算 U。
6. **事后补充（未预注册，第 9 节）：即使模型因此更早结束，B 也省不了钱。** 假设模型跳过所有"内容仍是原文"的重读，并在剪枝后的历史上重放，CR-2 n 里 B 能省掉 25.4% 的请求，每次运行输入中位减少 5.8%，但缓存估计费用中位仍然增加 9.6%，只有 39% 的运行变便宜。同样的假设下，C 的费用中位减少 22.4%，82% 的运行变便宜，而且不再出现超限请求。把"轨迹不变"和"完全剪枝"两个极端放在一起看：B 在两种情况下都更贵（+58% 到 +10%），C 在两种情况下都更便宜（−5% 到 −22%）。

## 1. 数据和方法

**运行。** 与重复读分析（`docs/analysis/REREAD-AND-PROMPT-TIMING.zh-CN.md`）相同：A5、A6-R、CR-2（排除基础设施重跑和失效运行），P4 提示时机 53 次和 P4 首轮 1 次。共发现 2083 个运行，排除 211 个（infra_retired 197、infra_error 12、invalid_candidate 1、unknown 1），这和重复读分析的排除一致，剩下 1872 个全部模拟成功。

**原始历史。** 遮蔽不增删消息，所以第 s 步的原始历史等于最后一次 `state.saved` 消息列表里、长度与第 s 步视图相同的前缀，并且要求它的哈希等于记录的 `raw_message_hash`。53,823 步直接满足。A5 b2 每个运行的第 0 步（共 153 步）多了 2 条只在那一次请求里注入的策略候选消息：原始历史只有 system 和 user 两条，哈希能和保存列表更短的前缀对上；这一步视图里没有 tool 消息，没有可遮蔽的内容，所以在所有规则下都直接用记录的视图。

**规则。**

| 规则 | 定义 |
|---|---|
| A | 现行：`WindowPolicyHooks`，strategy masking，`keep_recent=4`，保护规则 v1，`preserve_tools` 为空 |
| B | A 改为 `keep_recent=8` |
| C | 先按 A 遮蔽，再把读过文件（lines/tail 读取单元）的工具结果恢复为原文，直到后面某次写入触及它读过的文件。写入判定沿用重复读分析（包括"运行了代码"和无法识别的写入）。搜索结果和其他结果仍按 A。只在分析脚本里实现，未改 `src/` |
| BC | B 加上 C 的保护 |
| N | 不遮蔽，作为省调用和请求大小两方面的上限 |

**指标。** 假设模型在每条规则下做出与记录完全相同的调用（见第 7 节）。

- **可避免的重复读**：一次重复读（沿用重复读分析的定义），它重复的每个读取单元，在模拟视图中都被此前原文覆盖至少 80%（"原文"状态）。"原文或部分原文"把 20–80% 覆盖也算进去，只作描述。
- **输入 token**：每次请求的 `calibrated_v1` 准入 token，调用 `src.runtime.window.request_size`。A5、A6-R 的运行目录里没有工具定义文件，工具个数和字节数由第 0 步记录的统计反推；所有步骤反推出的字节数和准入 token 都与记录一致（不一致 0 步）。
- **准入**：输入加上记录的预留输出（8192）超过 96,000 即算拒绝，和 harness 的判定相同。
- **费用**：价格取 `scripts/cr2_cost.py`（命中 0.04、不命中 2.00、输出 8.00 元/百万 token）。先用每个运行在记录视图上的"provider `prompt_tokens` ÷ `calibrated_v1`"比例，把 token 折算成 provider 单位。(a) 上界：全部输入按不命中价格计。(b) 前缀缓存估计：与上一次请求视图开头相同的那些消息加上工具定义，算作命中，按 64 token 向下取整。输出 token 在所有规则下都取记录值。
- **只含可避免重读的请求**：一步里的所有调用都是可避免的重复读，这是该规则最多能省掉的模型调用数。去掉这些请求后的输入合计只是粗算，没有考虑之后的视图也会随之变化。

## 2. 预注册

阈值和决策规则写在 `scripts/analysis/context_sim/sim.py` 的模块说明里，在提交 `0dd56ba` 中提交。提交前只运行过规则 A 的冒烟测试。

- 决策组：CR-2 n（计划中付费实验的 prompt 和题目），其他组只作报告。
- 候选：B、C、BC；A 和 N 作为参照。
- T1：可避免（原文）重复读占全部重复读 ≥ 50%（按调用合计）。
- T2：每次运行的输入 token 相对 A 的增幅，中位数 ≤ 30%。
- T3：每次运行的前缀缓存估计费用相对 A 的增幅，中位数 ≤ 30%。
- T4：没有请求超过 96,000 `calibrated_v1` token（含预留输出）。
- 在通过 T1–T4 的候选里选可避免比例最高的；相差 5 个百分点以内时，选 T2 增幅更小的。没有候选通过时，报告没过的测试，不建议为该规则付费。
- 付费实验主指标：U = 推荐规则在 CR-2 n 的可避免重读 ÷ 工具调用。U ≥ 15 个百分点时，保留第 6 节的主指标和阈值（B − A ≤ −10，区间上界 < −5）；U < 15 时，即使轨迹不变也达不到 −10，不按原设计执行。

**预注册之后的改动**（没有改动阈值、指标定义和决策逻辑）：

1. 第一次全量运行时，A5 b2 的第 0 步原始历史哈希对不上，导致运行出错。改为按第 1 节描述的顺序查找原始历史，并且只在哈希能验证的情况下使用；同时单个运行出错时记录状态并继续，不中断全量运行。最终 0 个运行出错。
2. 并行执行改为每完成一个运行就追加写盘，可续跑。原来的写法在 Windows 上两次挂起。
3. 汇总里和重复读分析逐条比对时，参照集合限定为本次纳入的运行（原来包含被排除运行的重复读，会出现假的不一致）。

## 3. 核对

**规则 A 复现。** 1872 个运行、53,976 步，模拟视图和记录视图逐条相等，视图状态也全部相等，差异示例为空。

**和重复读分析一致。** 每个运行的重复读次数 1872 / 1872 相同；重复读调用集合完全相同（21,069 次）；记录视图下每次重复读的视图状态（原文 / 部分 / 已遮蔽 / 不在视图）21,069 / 21,069 相同。

**token 估计。** `calibrated_v1` 明显高估 provider 实际计费的 token。在 52,998 个有用量记录的请求上，provider `prompt_tokens` ÷ `calibrated_v1` 的中位数是 0.454（p10 0.417，p90 0.494，最大 0.895）。也就是说，96,000 的准入上限扣掉预留输出后，大约相当于 4 万 provider token。费用一律先按每个运行自己的比例折算。

**缓存估计。** 在记录视图上，从每个运行的第 2 次请求起，估算的命中占比是 72.2%，provider 实际是 67.1%；各实验的估算都比实际高 2–5.5 个百分点（A5 74.5 / 69.5，A6-R 75.7 / 71.1，CR-2 70.4 / 64.9，P4 69.6 / 67.6）。估算的总费用 278.2 元，按 provider 用量算是 302.4 元，比例 0.92。估算略偏乐观，但幅度稳定，用来比较规则之间的相对差别是够用的。

## 6. 事后观察（未预注册，仅供设计下一步参考）

- **省下的调用不足以抵消 B 的缓存损失。** CR-2 n 里 B 有 28.8% 的请求只含可避免的重复读。粗略假设这些请求全部省掉、其余请求费用不变，B 的缓存估计费用约 69.3 × (1 − 0.288) ≈ 49.3 元，仍比 A 的 43.3 元高约 14%。
- **C 的方向在费用上占优，问题在请求大小。** C 的缓存估计费用在 CR-2 比 A 低约 5%，A5、A6-R 持平，P4 低 14–19%；可避免重读 62–91%（P4 首轮只有 1 次，不计）；没通过的是长运行里的输入增长和准入超限。可以考虑的下一个候选是"C 加一个大小上限"：保护的原文合计超过某个预算时，从最早的开始遮蔽。另一个方向是"批量遮蔽"：不每步滑动，而是在视图接近预算时一次性遮蔽一批旧结果，让前缀在多数步骤里保持不变。这两条都需要先写好阈值，再按本文方法离线模拟，然后才考虑付费。
- **96,000 准入上限按 `calibrated_v1` 计算偏保守。** 它按实际 provider token 只相当于 4 万左右。如果要把 C 一类规则付诸实验，应该先确认准入预算是否要按更准确的估计调整，否则 T4 主要反映的是估计方法的偏差。

## 7. 局限

- **轨迹不变的假设。** 所有数字都假设模型在每条规则下做出与记录完全相同的调用。实际上，原文还在时模型可能不重读，于是后面的视图、步数和费用都会改变；"可避免"是上界，不是预测。规则 A 下仍有 8.2% 的重复读发生在原文就在视图里的时候，说明原文可见并不保证模型不重读。省掉请求之后的输入和费用只做了粗算（第 4.1 节最后一行、第 6 节第一条）。
- **单一模型，单一价格。** 用量比例和价格都来自这批 DeepSeek 运行。缓存估计假设 provider 能命中"与上一次请求相同的前缀"，按 64 token 取整，在记录视图上比实际命中高约 5 个百分点（费用估算为实际的 0.92）。规则之间的相对差别依赖于"偏差在各规则下相近"这个假设，没有直接验证。
- **规则 C 的写入判定沿用重复读分析。** 运行代码的命令只视为改动工作区外和构建目录。如果某条命令改了源码却没被识别，C 会继续保留过期的原文，可避免比例会偏高、请求会偏小。重复读分析的留出样本里没有遇到这种情况。
- **重复读定义的局限照搬。** 是否重复只看参数推断出的行范围和搜索模式，搜索要求模式完全相同，所以重复读本身偏低估。
- **工具定义是按字节数构造的替身。** A5、A6-R 没有工具定义文件，用纯 ASCII 替身复现了记录的字节数和准入 token（全部一致）。CR-2 的工具定义经检查全是 ASCII，`calibrated_v1` 对替身和真实定义的结果相同。
- **P4 样本很小。** P4 三组各 17–18 次，首轮只有 1 次，只作描述。

## 9. 事后补充：假设模型跳过内容仍可见的重读

这一节在看到第 4、5 节结果之后才设计，没有预注册，只用来回答"保留更多原文会不会让任务更早结束、反而更省"。

**方法**（`scripts/analysis/context_sim/pruned.py`）。沿记录的轨迹逐步向前，维护一份剪枝后的历史。每一步先按规则生成视图，再用第 1 节的重复读判定检查这一步的调用，此前的读取只算保留下来的调用。如果一次调用是重复读、重复的每个读取单元在视图里都是原文、本身不写文件也不运行代码，就假设模型不发这次调用：它和对应的结果都从历史中删去，这一步的 assistant 消息只保留其余调用。一步里的调用全被删掉时，这一步不发请求，下一步用同样的历史提问。之后每一步的视图都在剪枝后的历史上重新生成，所以"历史变短"和"窗口里留下更多旧结果"的连锁效应都算在内。token、缓存估计和费用的算法和第 1 节相同，输出 token 取保留步骤的记录值。基线是规则 A 的实际记录（不剪枝）。

**自检。** 关闭剪枝、用规则 A 重放，1719 个运行、50,429 步重建出的历史和记录的原始历史逐条相同。A5 b2 的 153 个运行第 0 步有注入消息，历史不是保存列表的前缀，没有纳入这一节；A5 剩下 224 个 b0 和 15 个 b2。

**结果**（相对 A 的实际记录；费用为缓存估计，每次运行增幅的中位数，括号内为 p10 / p90）：

**解读。**

- **B 省了请求，省了一点 token，但没省钱。** 在 CR-2 n 里，B 能省掉四分之一的请求，输入总量也略降，但每一步缓存不命中的部分更长，费用中位仍然增加约 10%，合计费用和 A 持平或略高。A5、A6-R 里 B 省掉的请求更少（8–13%），费用增加 23–25%。
- **C 在两个极端下都更便宜。** 轨迹不变时 C 的费用中位是 −5%（第 4.1 节），完全剪枝时是 −22%；第 4.4 节的超限请求在剪枝后全部消失，因为跳过重读后历史变短了。C 的风险在于真实情况更接近"轨迹不变"时输入和请求大小的增长（第 4.1 节 p90 +109%）。
- **A 本身剪枝只省 3%。** 这说明模型在现行规则下很少重读仍可见的内容，"内容可见就不重读"这个假设和记录的行为大体一致。但规则 A 下仍有 8.2% 的重复读发生在原文可见时（第 7 节），所以本节是乐观的上界。

**限制。** 假设模型跳过的恰好是这些调用，其余决策、输出长度和结束时间都不变；实际上省下的步数可能用来做别的事，也可能更早结束。本节不估计解出率：重复读分析第 3.3 节显示，控制运行长度以后，重复读和是否解出几乎无关。

**对下一步的含义。** 如果要做付费实验，比较的对象应该是 A 对 C（或 C 加大小上限），不是 A 对 B；成本护栏应该用 provider 实际计费（含缓存命中），不能只看输入 token。阈值需要在实验前另行写定。
