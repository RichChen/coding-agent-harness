## 2. 威胁有效性的问题，以及处理

1. **6 个 `infra_kept` 槽位。** 三次运行里都出现过网络失败，退役次数用完后按冻结规则保留。它们都跑满了 40 次调用，status 正常。处理：主分析计入，S1 去掉它们。占全部的 0.5%。
2. **服务端在运行中途换过版本。** `system_fingerprint` 在 10-27 18 点前后从 `e72d3c7f…` 换成了 `bc19ba97…`，模型名始终是 `deepseek-flash`。两段时间里四组都有，都是交错运行，组间比较依然公平。处理：S3 只用后一段的运行。
3. **`delta_too_large` 集中在一道题。** `scikit-learn-12585` 的 20 个槽位里有 11 个没有候选补丁，各组分布不均。主指标不受影响，但这道题的修复率差值可能被放大。处理：S2 去掉这道题。
4. **退役重跑会偏向短运行（我新发现的）。** 每次模型调用的网络失败率约为 0.43%（161 / 37,718）。一次 40 步的运行碰到失败的概率约 16%，10 步的约 4%。被退役的多半是长运行，而长运行多半是没解出的运行。所以"最终运行"整体会偏短、偏成功。各组的运行长度不同（O 组可能更短），这个偏差在组间也可能不一样大。处理：S4 改用每个槽位第一次不是 infra_error 的运行。这样只按错误类型选，不再因为网络失败而重抽。
5. **墙钟 42 小时 46 分，估算是 23 小时。** 主要原因是 159 次退役重跑（占 14%）和大量网络重试。不影响有效性。

## 3. 过程问题

- **合同第 9 节的乱码是我的错。** 我给出的 PowerShell 追加命令在 Windows PowerShell 5.1 下默认按 GBK 写入。现在已经按原文恢复，Cursor 当时还原后的理解与原文一致。以后追加文本都用 Python 按 UTF-8 写入。
- **来源不明的第二次启动又出现了一次**，在 07:12，runner 正常退出约 2 分钟后。它没有跑任何槽位，但覆盖了 `main.out` 和 `main-report.json`，并重写了 `cr2-runs.json`。两次都发生在 runner 正常退出之后，很可能是 Cursor 那边执行后台命令的机制在重试或重连，但没有证据。处理：分析前从运行目录重新生成一份 runs 文件，核对与入库的版本相同（合同 10.3）；之后不再运行正式模式。
- **系统待机。** 这次是 Cursor 自己关掉、跑完再恢复的，做法正确。
