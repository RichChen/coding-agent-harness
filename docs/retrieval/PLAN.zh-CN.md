# CR：可评测的代码知识检索与验证记忆层

日期：2026-10-18。读者：项目作者、Cursor 执行模型、阶段末复核的 Codex。

本文是 CR 线的总体方案。每一层的执行细节写在单独的任务合同里，第一份是 [CR-1 合同](CR-1-CONTRACT.zh-CN.md)。`docs/rsi/` 的反馈策略快速版不再按原规模执行，它的"候选、评测、晋升"思路并入第三层。

## 1. 要回答的问题

给一个 issue，系统能不能找到需要修改的代码；找到之后，agent 有没有因此更快定位；从历史修复里沉淀的定位知识，能不能经过质检后让检索变好。

三层各自产出能独立成立的结果：

| 层 | 问题 | 主指标 | 花费 |
|---|---|---|---|
| CR-1 离线检索 | BM25、embedding、混合排序谁更能找到 gold 文件 | 文件级 hit@5、MRR，按题配对 | 0 元模型费，本地 GPU |
| CR-2 接入 agent | 检索结果能不能让 agent 更早打开正确文件 | 首次读到 gold 文件的步数，按题配对 | 小批付费运行，额度在 CR-2 合同里定 |
| CR-3 定位知识卡 | 从更早的修复里沉淀的卡片，经过离线门槛后能否提升留出题检索 | 留出题 hit@5 / MRR 变化、误触发率 | 卡片生成的少量模型调用 |

修复率只在 CR-2 里描述，不作为主结论。A5/A6 已经说明几十道题的修复率测不出中等效应。

## 2. 固定的边界

- **答案隔离。** 检索输入只能是 `problem_statement` 加 base_commit 的仓库快照。`patch`、`test_patch`、`hints_text`、`FAIL_TO_PASS`、`PASS_TO_PASS` 只能出现在标签模块里。靠模块边界和测试保证，不靠约定。
- **调参与报告分开。** 所有选择（切块方式、tokenizer、embedding 型号、RRF 参数、文件聚合方式）只在 dev 上做。冻结后 test 只跑一次。
- **A5/A6 不动。** A5 主实验题单（main-targets）与干净镜像题的并集共 62 道，全部放进 test，不参与调参，以后 CR-2 从里面选题。
- **不预写结论。** hybrid 不一定赢 BM25：issue 里常有函数名和异常栈，BM25 本来就强。三种结果都按实际报告。
- **定位要诚实。** BM25 在 SWE-bench 上的定位结果已有公开报告（SWE-bench 原论文、Agentless 等）。CR-1 是复现加系统化评测，不宣称新方法。

## 3. CR-1：离线检索（已写合同）

数据：本机缓存的 SWE-bench Verified，500 题，12 个仓库，499 个 base_commit。86% 的 gold patch 只改 1 个文件，文件级指标干净。

做法概要：

1. 在仓库外的缓存目录里 clone 12 个仓库，按 base_commit 用 `git ls-tree` / `git cat-file` 读文件，不做 checkout。
2. Python 源文件按 AST 切成函数、类、模块级块；解析失败退回按行窗口。以 git blob sha 为键缓存切块、tokenize 和向量，跨 commit 复用。
3. 三个检索器：自写 BM25（代码感知 tokenizer）、本地 embedding、RRF 融合。另有两个参照：随机排序，以及"issue 里是否直接出现文件路径/模块名"。
4. 标签：gold patch 改动的非测试文件；函数级标签由改动行映射到 base 文件里包住它的函数或类。
5. 指标：文件级 hit@1/5/10、全部 gold 文件 recall@10、MRR；函数级 hit@5/10；按仓库拆分；按题 paired bootstrap 区间。

## 4. CR-2：接入 agent（CR-1 结束后写合同）

已有的 `search_code` 是正则 grep（`src/tools/search.py`），b0-v2 已启用。新工具另起名字（暂定 `retrieve_code`），在宿主上查询离线建好的索引，按 repo + base_commit 定位。宿主索引不读容器工作区，所以只适用于 agent 修改前的快照，返回结果要声明这一点。

需要改的地方：`factory.py` 的 Docker 工具白名单、工具注册、`src/eval/tool_errors.py` 的工具列表；结构化结果给 `ToolResult` 加可选字段，并处理 `previous_result` 重建和运行时指纹的变化。

分组等 CR-1 结果再定。候选是：基线（只有 grep）、检索工具、预取（把 top-k 文件列表直接放进 prompt，确保检索结果被看到）。如果 BM25 与 hybrid 离线差别很小，端到端只保留一种。

## 5. CR-3：定位知识卡（CR-2 结束后写合同）

卡片沉淀的是定位知识，不是修复经验。例如"这类描述通常对应哪些模块或文件"，来源是同一仓库更早的已修复 issue。

- 时间切分：目标题只能使用 `created_at` 早于它的修复。这些修复本来就是仓库里的公开 commit。
- 模型只提出候选卡片，宿主校验格式、来源和适用范围。
- 晋升门是离线的：在留出题上，加入这张卡后检索不能变差，并且误触发要低于阈值。阈值在看结果前写进 CR-3 合同。
- 被拒绝的卡片和原因全部保留，可以回滚到无卡片版本。

这一层对应岗位描述里的"知识生成、沉淀、进化、质检"，而且能在 400 道留出题上测，不依赖昂贵的端到端运行。

## 6. 协作方式

| 角色 | 职责 |
|---|---|
| 项目作者 | 确认方向和预算；在每个检查点前读一遍检查点文件；自己设计 CR-3 的卡片格式 |
| Claude Code | 写方案和合同，审计每个检查点 |
| Cursor 执行模型 | 按合同编码、运行、写检查点，然后停下 |
| Codex | 每层结束后复核目标、证据和表述 |

检查点和审计文件放在 `docs/retrieval/`，命名沿用 `CHECKPOINT-CR-1a.md`、`AUDIT-CR-1a.zh-CN.md`。交接文件的 sha 按 [HANDOFF-CONVENTIONS](../sprint/HANDOFF-CONVENTIONS.md) 计算。
