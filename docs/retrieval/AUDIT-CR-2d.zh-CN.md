## 3. 结果怎么解读

1. **离线检索有效，但在这批题上，agent 自己定位得已经很快。** N 组平均第 5.3 步就打开了正确文件，91.8% 的运行在前 10 步以内。所以预取（P）没有让定位更早：P−N 为 −0.02 步，区间 [−1.87, 2.05]。
2. **即使直接告诉它正确文件（O），修复率也没有检出变化。** O−N 为 +2.1 个百分点，区间 [−5.4, 9.6]。O 组确实更早打开正确文件（−2.4 步），但修复率没有跟着变。在这 56 道题上，瓶颈不在"找到哪个文件"，而在之后的理解、修改和验证。这和 CR 计划里写的"检索提升不一定转化为修复率"一致。限度：56 道题只能排除较大的效应，区间上限 +9.6 个百分点并不小。
3. **给了检索工具，模型一次也没有用（0/280）。** T 组测到的只是"工具列表里多了一个没被用的工具"，没有坏处（T−N 修复率 −0.7 [−5.4, 3.9]），也没有测到检索本身的作用。这是 agent 系统里的一个实际问题：工具存在不等于会被调用。在不改 system prompt 的前提下，模型更信任它熟悉的 grep。
4. **唯一区间不含 0 的次要差异：P 组少用 1.85 次模型调用**，区间 [−3.47, −0.45]；O 组少用 1.30 次。费用差异未检出。

## 4. 没有预注册的观察：同样的提示，解出率比 A5 低很多

CR-2 的 N 组与 A5 的 B0 用同样的 56 道题，首条消息、工具 schema、配置逐字节相同（兼容性测试和 summary 里的 `prompt_sha256` 都核对过）。可是：

| | A5 B0（9 月下旬） | CR-2 N（10-27 至 10-29） |
|---|---|---|
| 解出率 | 68.5%（115/168） | 45.7%（128/280） |
| 用满 40 次调用的比例 | 27.4% | 58.2% |
| 平均模型调用次数 | 23.6 | 30.2 |

以上数字由 `runs/cr/audit_cr2d.py` 从两边的 summary 直接算出（项目作者在本机运行）：

- 56/56 道题的首条消息 sha256 在 A5 B0 和 CR-2 N 之间完全相同。
- 按题配对，CR-2 N 减 A5 B0 的解出率为 **−22.7 个百分点，区间 [−32.6, −13.5]**。26 道题变差，27 道不变，3 道变好。这是普遍下降，不是少数题造成的。
- 每次运行花在重试或失败尝试上的模型调用平均只有 0.03 次，解释不了"用满 40 次"的比例翻倍。

同一个脚本也独立重算了 CR-2 的结果：首次触碰步数均值 N 5.289、P 5.264、T 5.386、O 2.871；P−N −0.025、T−N +0.096、O−N −2.418；解出数 N 128、P 136、T 126、O 134；T 组 `retrieve_code` 调用 0 次。与 `cr2-analysis.json` 一致。

还要说明一点：compat 基线核对的是首条消息、工具 schema 和运行时指纹在 CR-2 改动前后相同；首条消息又与 A5 的 summary 一致。但运行时指纹在 A5 当时的值没有记录，A5 到 CR-2 之间的提交里不能完全排除 loop 行为的变化。这些提交主要是文档、不再跟踪的文件和阅读注释，所以可能性小，但没有逐项证明。最可能的原因是服务端模型变了：DeepSeek 价格页写明 `deepseek-flash` 现在由 `V4.1-Flash-1017` 提供，旧模型已下线；CR-2 运行期间 `system_fingerprint` 也换过一次。

这一点不影响 CR-2 的结论，因为四组都在同一个模型上交错运行。但它对整个项目很重要：**同一个别名、同一份提示，服务端更新后，解出率在同一批题上从 68.5% 掉到 45.7%。** 只看别名去引用旧实验的数字是不安全的。这也说明 CR-2 坚持同期交错对照、不和 A5/A6 比数值，是对的。

它是事后观察，没有预注册；时间、模型版本和 harness 的提交都同时变了，不能作为因果结论。`audit_cr2d.py` 里也算了按题的配对差值，作者运行后补进结果文件。

## 5. 重复执行

到现在已经三次了：runner 两次正常退出后各被同样的命令再启动一次，这次一条前台 pytest 也被执行了两次。都没有造成数据变化。证据指向 Cursor 执行命令的机制，而不是项目代码。以后有副作用的命令应该自己检查完成标记，比如 runner 在 `cr2-runs.json` 已完整时拒绝正式模式。这留作以后的改进，本轮不改冻结代码。
